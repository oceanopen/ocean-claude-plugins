# 任务拆分文档契约

定义任务拆分文档的结构与更新规则。生成方（`/ocean-code:task-split`）必须遵守本契约；执行方（开发 Agent / 人工）按文档头部内置的「状态回写规则」更新状态——本契约是该规则的源头，回写规则随文档模板内置，执行方无需读本技能即可遵循。

**文档即进度 SSOT**：子任务清单、状态、进度只记录在任务文档一处，不在 CLAUDE.md / issue 描述等其他位置另建副本，杜绝双写漂移。

## 文件位置

```
{项目根}/docs/task_<主题>.md    # 主题 slug 从需求推导，小写英文 + 下划线（如 docs/task_bot_binding.md）
```

**模板硬性约束**：

- 状态只出现在两处——头部「状态」总览行与每任务的「**状态**」字段，正文其他位置不冗余记录进度
- 「实施定稿」段落不在生成时写入——由执行方完成任务后按回写规则补写
- 生成时全部任务状态为 ⬜；生成方不置 🔲/✅（状态流转是执行方的事）
- 按需裁剪：小需求可省略 §2/§3（省略后剩余章节编号顺延重排），任务清单可单阶段不分级（直接 `#### T1` 形式）；无代码上下文时 §1.1 现状事实表可省略

## 状态回写规则

规则源头在此，实际载体是每份文档头部的同名段落（模板已内置）：

- **置 🔲**：任务开始执行时
- **置 ✅ + 补实施定稿**：任务完成、对照验收逐条核验通过后；实施定稿只记实施终态与相对方案的偏离（含拍板修正、落位调整、补充的终态事实），作为当前事实陈述——不写日期、不写演变叙述，变更历史归 git
- **头部总览行同步**：首个任务开始时置「实施中」，全部任务 ✅ 后置「已完结」
- **不主动 git commit**：回写只改文档，提交动作必须经用户明确确认
- **偏离先行修订**：实施中若需偏离方案，先修订文档对应设计段落再动代码，保证文档始终是当前事实

## 子任务拆分规范（task-split 执行）

- **可验证**：每个任务必须有明确验收（可逐条核验的判据），杜绝「优化一下」「完善功能」类表述
- **粒度适中**：一个任务 = 一次可独立验收的交付；避免过细（纯机械步骤）与过粗（跨多模块大改）
- **依赖排序**：被依赖者排前；相互独立的任务可同阶段并列
- **阶段划分**：多任务时按交付边界分阶段，每阶段独立可交付、阶段间依赖显式标注
- **数量建议 3~8 项**：小需求不硬拆（仅 1~2 项时建议不拆直接执行）

## 增量重跑规则（task-split 执行）

目标文档已存在时的修订约束：

- **已完成任务（✅）永不回改**：状态与「实施定稿」段一律不动；对其提出的需求变更以新增任务承载
- **进行中任务（🔲）**：需求变更影响其方案时，先经用户确认再修订对应段落
- **未开始任务（⬜）**：可新增、修订、删除（删除须用户确认）；新增任务编号顺延，不复用已删除编号
- **头部总览**：「状态」行随实际进度如实更新；范围/基线等元信息按需求变更同步修订
